## SDD_2：小任务顺手 vs 复杂任务失控
- 小任务顺手：
  - 目标短，变量少
  - 上下文还在窗口里
  - 做完就结束，不需要接力
  - 出错范围通常比较小
- 复杂任务失控：
  - 目标会持续变化
  - 边界和状态容易丢
  - 要跨文件跨阶段接力
  - 没有统一验收就会越做越偏
- 原图特点：左右对比版式；左侧闪电图标代表“小任务顺手”，右侧拼图图标代表“复杂任务失控”；中间有圆形“VS”；右侧要点用黄色项目符号强调。

## SDD_3：复杂开发失控的四个原因
- 目标漂移：需求边做边变，没人收口
- 边界不清：可改范围只在聊天里提过
- 状态丢失：上一轮决定没有沉淀下来
- 验收模糊：没有一致的完成标准
- 结论：这些都不是单次回答的问题，而是过程设计的问题。
- 原图特点：中心橙黄色圆点写“复杂开发为什么会漂”；四张编号卡片围绕中心分布，并用虚线连接；底部有橙色强调条写“这些都不是单次回答的问题，而是过程设计的问题”。

## SDD_6：聊天记录 vs 书面约束
- 只有聊天记录：
  - 目标讲过但没留底
  - 边界靠上下文记忆
  - 做到哪里凭感觉
- 有书面约束：
  - 目标有明确描述
  - 边界写进任务入口
  - 验收标准先定义好
- 结论：不要把复杂任务一直留在聊天里，而要先沉淀成可对照的约束。
- 原图特点：左右两栏对照；左侧偏灰暗，右侧偏蓝；左栏是“只有聊天记录”，右栏是“有书面约束”；底部字幕强调“它不是让你多写一堆流程文档，而是先把事情说清”。

## SDD_14：常见误解 vs 真正要补的
- 常见误解：
  - 先写一堆文档
  - 写完放着不更新
  - 项目一忙就回到裸聊
  - 最后只剩形式感
- 真正要补的：
  - 给实现建立事实来源
  - 让 review 有共同参照
  - 让验证能对齐需求
  - 让变更可以追溯和交接
- 结论：价值不在“写了什么”，而在“后面是否真的按它推进”。
- 原图特点：左右对比栏；左侧用文档图标表示“常见误解”，右侧用图钉图标表示“真正要补的”；底部字幕强调“共同事实来源”。

## SDD_15：没有 spec vs 有稳定 spec
- 没有 SPEC：
  - 目标靠聊天补充
  - 边界一忙就忘
  - 做完靠直觉判断
- 有稳定 SPEC：
  - 目标可回看
  - 边界可对照
  - 验收可执行
- 结论：spec 提供持续对齐能力。
- 原图特点：左右两栏对比；左栏标题是“没有 SPEC”，右栏标题是“有稳定 SPEC”；左右均使用复选框列表，右栏色调更亮。

## SDD_18：SDD 在更上层收口
- TDD：先写测试，定义代码行为
- BDD：先写行为，强调用户视角
- 技术规格：架构约束与实现前提
- 需求规格：功能目标与边界条件
- SDD：把不同阶段的约束收进一份可执行事实来源。
- 原图特点：中心橙色圆点写“SDD”；四张卡片围绕中心，分别是 `TDD`、`BDD`、`技术规格`、`需求规格`；用虚线连接形成概念网络。

## SDD_19：更完整的 spec 内容
- 目标与价值：解决什么问题，为什么现在做
- 上下文与约束：依赖什么，受什么限制
- 输入输出：谁给什么，最后产出什么
- 边界条件：异常、反例和禁止项
- 验收标准：做到什么程度才算完
- 技术要求：性能、安全、可维护性
- 原图特点：六张窄卡片横排，编号 `01` 至 `06`；每张卡片突出一个 spec 组成部分；整体像清单墙。

## SDD_20：什么时候不必重工程化
- 可以先别上太重：
  - 探索型原型
  - 一两行的小改动
  - 紧急修复先止血
  - 强主观的临时试验
- 值得走 SDD：
  - 复杂功能迭代
  - 多人或多 agent 协作
  - 需要 review 和追溯
  - 做偏了返工很贵的任务
- 结论：不是所有地方都要工程化，但复杂任务不能一直靠感觉推进。
- 原图特点：左右对比栏；左侧绿色小图标代表“可以轻一点”，右侧橙色工具/锤子图标代表“值得走 SDD”；底部字幕用黄色强调边界。

## SDD_22：一个功能级 spec 最小轮廓
- 示例目标：给订单列表增加导出能力
- 边界：只改列表与导出链路，不重构查询模块
- 输入输出：选择条件 → 导出文件
- 异常：无权限、导出超时、空数据
- 验收：接口可回归，结果可下载，日志可追踪

## SDD_23：review 顺序也会变化
- Step 1：先看目标和边界有没有写清
- Step 2：再看验收标准是否可执行
- Step 3：最后再看代码实现是否对齐 spec
- 价值：review 不再只是盯 diff，而是对齐共同事实来源。
- 原图特点：终端窗口样式；逐行展示 `Step 1`、`Step 2`、`Step 3`；底部字幕强调 review 先看意图和约束。

## SDD_26：重流程体验 vs OpenSpec 体验
- 重流程体验：
  - 阶段很多
  - 命令记不住
  - 先学工具再做需求
  - 团队很容易半路放弃
- OpenSpec 体验：
  - 主路径很短
  - 四个动作容易形成习惯
  - 先解决需求，再补流程细节
  - 更适合日常迭代
- 原图特点：左右对比栏；左侧偏灰，右侧偏蓝；左侧图标偏“文档/流程”，右侧图标像羽毛，突出轻量感。

## SDD_27：OpenSpec 主路径概览

- 原图特点：中心橙色圆点连接四张卡片；四张卡片分别写 `Explore`、`Propose`、`Apply`、`Archive`；底部橙色强调条说明主路径短。

- 可评审：先审意图，再审实现

## SDD_30：结构化工作链 vs 只有聊天记录
- 只有聊天记录：
  - 讨论完就散
  - 后续靠记忆恢复
  - review 只能看 diff
- 有结构化工作链：
  - 意图、方案、任务分层沉淀
  - 后续可按文档恢复上下文
  - review 可以分阶段看问题
- 价值：结构化工作越主路径，协作越不像碰运气。
- 原图特点：左右对比版式；左侧列表描述聊天记录的局限，右侧列表描述结构化工作链；底部字幕出现 OpenSpec 主路径说明。

## SDD_32：OpenSpec 默认留下什么
- proposal：解释为什么做这次改动；影响范围与风险
- design：记录实现路径和关键决策；技术方案与取舍
- tasks：拆成可执行清单；按任务推进并勾选
- specs：并回系统的长期规范；避免文档腐烂
- 价值：这些不是摆设，会直接影响 review、回顾、接手和后续迭代。
- 原图特点：四张横向卡片；标题为“OpenSpec 默认留下什么”；卡片名分别是 `proposal`、`design`、`tasks`、`specs`。

## SDD_33：一条最小 OpenSpec 工作流
- 安装：`npm install -g @fission-ai/openspec@latest`
- 初始化：`openspec init`
- Explore：`/opsx:explore 给订单列表加导出功能`
- Propose：`/opsx:propose 增加订单导出能力`
- Apply：`/opsx:apply`
- Archive：`/opsx:archive add-order-export --yes`
- 核心路径：先初始化，再 explore，再 propose，再 apply，最后 archive。
- 原图特点：终端窗口样式；绿色命令行展示安装、初始化和 slash command；底部字幕说明流程只需要记住几个动作。

## SDD_34：探索阶段 vs 生产迭代
- 探索阶段：
  - 先跑出方向
  - 问题还在收敛
  - 可以先轻量一点
  - 后面再决定是否补规范
- 生产迭代：
  - 要考虑 review 与回溯
  - 改动要能交接
  - 存量系统不能随便漂
  - 更适合走完整规范闭环
- 结论：OpenSpec 更像生产级迭代主路径，不是替代所有探索行为。
- 原图特点：左右对比栏；左侧像笔形图标代表探索，右侧文档图标代表生产迭代；中间有 `VS`，底部字幕强调“不是所有任务都一上来走完整流程”。

## SDD_35：多智能体协作的三步
- 先 init：在项目里把规范层入口补起来；不用先追求复杂模板
- 先 propose：先生成可评审工作再实现；别一上来就 apply
- 做完 archive：把一次变更并回系统规范；避免文档慢慢失真
- 原图特点：三张横向编号卡片；标题分别为“先 init”“先 propose”“做完 archive”；卡片上方有 `01`、`02`、`03` 编号。

## SDD_37：SDD EP04 开篇
- 主题：SDD 开发模式

## SDD_38：直接并行开干 vs 先文档再并行
- 直接并行开干：
  - 每个 agent 自己理解需求
  - 接口和字段容易漂移
  - 合并时才暴露冲突
  - 返工成本很高
- 先文档再并行：
  - 目标和边界先写清楚
  - 任务按交付单元拆开
  - 接口和验收先对齐
  - 并行时更容易稳定收口
- 结论：协作不是把任务扔出去，而是先把共同事实立住。
- 原图特点：左右对比栏；左侧用爆炸/警告类图标表达风险，右侧用时钟/稳定图标表达可控；底部有黄色强调字幕。

## SDD_39：多智能体协作的共同事实
- Goal：这次到底要交付什么
- Design：关键方案与边界怎么定
- Contracts：接口、字段、输入输出
- Acceptance：做到什么算完成
- 要点：多智能体要跑顺，先把共享事实从聊天变成文档。
- 原图特点：中心橙色圆点写“共同事实来源”；四张卡片围绕中心，分别为 `Goal`、`Design`、`Acceptance`、`Contracts`；底部橙色强调条突出共享事实。

## SDD_40：一次典型并行翻车链路

- 原图特点：终端窗口样式；逐行展示 Agent A/B/C 的动作；最后用红色错误行突出“接口契约不一致”；右上角仍有 `CLAUDE CODE` 标识。

## SDD_41：按人分活 vs 按交付单元拆
- 按人分活：

  - 边界常常后置
  - 合并时才发现不匹配
- 按交付单元拆：
  - 先定输入输出
  - 接口契约先锁定
  - 每块都有完成标准
- 结论：多智能体并行之前，最关键的是拆解方式。
- 原图特点：左右对比栏；左侧描述“按人分活”，右侧描述“按交付单元拆”；底部字幕强调“不是谁去做，而是怎么拆”。

## SDD_47：并行条件
- 先别并行：
  - 接口还在变
  - 字段命名没锁定
  - 验收门不明确
  - 写域互相覆盖
- 可以并行：
  - 输入输出已固定
  - 契约已经成文
  - 任务边界互不干扰
  - 完成标准都能独立检查
- 结论：并行不是默认动作，很多任务其实应该先串行收口。
- 原图特点：左右对比栏；左侧用红色禁止图标表示“先别并行”，右侧用绿色勾表示“可以并行”；底部字幕强调先判断并行条件。

## SDD_52：最小闭环四动作

## SDD_56：Archive 的作用
- 不做 Archive：
  - changes 只停在临时目录
  - 代码改了，主规范没更新
  - 后续继续迭代时又要猜
- 做 Archive：
  - 增量规范并回主 specs
  - 系统现状可回看
  - 后续迭代有统一入口
- 结论：archive 不是收尾动作而已，它决定文档会不会腐烂。
- 原图特点：左右对比栏；左侧是不做 archive 的问题，右侧是做 archive 后的收益；底部字幕用黄色强调 archive 会更新主规范。

## SDD_57：边做边验

## SDD_58：最少要盯住哪些验证门
- 边界门：有没有超出本次范围；避免顺手改太多
- 契约门：接口和字段是否一致；前后端都按同一份 spec
- 测试门：关键回归是否补齐；别把验证留到最后
- 检查项：是否偏离边界、接口是否对齐、测试是否补上、回归是否通过。
- 原图特点：三张横向卡片；标题为“最少要盯住哪些验证门”；卡片分别是“边界门”“契约门”“测试门”，每张卡片底部有蓝绿色标签。

## SDD_59：归档前后对比
- 归档前：
  - changes 仍停在临时变更目录
  - 代码变了，主 specs 没有更新
  - 后续迭代仍要靠人猜当前状态
- 归档后：
  - 增量规范合并回主 specs
  - 系统现状有统一入口
  - 后续开发可以基于最新事实继续推进
- 结论：做完不是只看代码合并，还要把事实来源同步回主规范。
- 原图特点：左右对比栏；左侧配文档/文件图标，右侧配红色归档/禁用感图标并形成 `VS` 对照；底部字幕强调“最后一步 archive，把事实来源带回系统”。
