## SDD_1：SDD 开发模式开篇
- 主题：SDD 开发模式
- 副标题：先把复杂开发为什么失控讲清楚
- 核心观点：任务一旦变成多文件、多步骤、还要改老项目，很快会开始漂。

## SDD_2：一次典型任务漂移
- 示例需求：给订单列表加导出按钮
- 漂移表现：
  - AI 先重构列表页结构、顺便统一目录
  - 新建临时结果目录
  - 测试未跑，验收条件未定义
  - 原任务从“加导出”漂成“顺手改一片”

## SDD_3：聊天记录 vs 书面约束
- 只靠聊天记录的问题：
  - 目标讲过但没留底
  - 边界靠上下文记忆
  - 做到哪里凭感觉
- 先有书面约束的优势：
  - 目标有明确描述
  - 边界写进任务入口
  - 验收标准先定义好

## SDD_4：先把过程立住
- 被划掉：继续堆 prompt
- 主张：先把过程立住
- 核心观点：复杂任务的关键，不是更会说，而是更会收口。

## SDD_5：小任务顺手 vs 复杂任务失控
- 小任务顺手：
  - 目标短、变量少
  - 上下文还在窗口里
  - 做完就结束，不需要接力
  - 出错范围通常比较小
- 复杂任务失控：
  - 目标会持续变化
  - 边界和状态容易丢
  - 要跨文件、跨阶段接力
  - 没有统一验收就会越做越偏

- 阶段 1：先讲复杂开发为什么会漂

- 阶段 4：最后讲多智能体与闭环

## SDD_7：先定义再实现
- 被划掉：边聊边写
- 主张：先定义再实现
- 核心观点：不是拖慢开发，而是把返工前置消化。

## SDD_8：SDD 先补的三件事
- 目标：这次到底解决什么问题；功能边界先写清
- 边界：哪些能动，哪些别碰；目录、接口、依赖约束
- 验收：做到什么程度才算完；测试、输出、回归结果

## SDD_9：复杂开发失控的四个原因
- 目标漂移：需求边做边变，没人收口
- 边界不清：可改范围只在聊天里提过
- 状态丢失：上一轮决定没有沉淀下来
- 验收模糊：没有一致的完成标准
- 结论：这些不是单次回答的问题，而是过程设计的问题。

## SDD_10：适合 SDD 的任务类型
- 存量项目：老代码边界多，最怕顺手乱改；需要“改一处牵一片”的控制
- 多人协作：人和 AI 都需要统一入口；不能靠聊天接力
- 长链路任务：需求、设计、实现要能收口；阶段产物必须可追踪
- 要 review 的任务：先看意图，再看实现；不只盯裸 diff

## SDD_12：从模糊需求到可执行约束
- 被划掉：模糊需求
- 主张：可执行约束
- 核心观点：不是增加流程，而是减少返工。

## SDD_13：SDD 到底在补什么
- 主题：SDD 不是多写文档，它到底在补什么
- 核心观点：复杂开发失控，往往不是 AI 不会写，而是过程没有被组织。

## SDD_14：SDD 在更上层收口
- TDD：先写测试，定义代码行为
- BDD：先写行为，强调用户视角
- 技术规格：架构约束与实现前提
- 需求规格：功能目标与边界条件
- SDD：把不同阶段的约束收进一份可执行事实来源。

## SDD_15：没有 spec vs 有稳定 spec
- 没有 SPEC：
  - 目标靠聊天补充
  - 边界一忙就忘
  - 做完靠直觉判断
- 有稳定 SPEC：
  - 目标可回看
  - 边界可对照
  - 验收可执行
- 价值：spec 提供持续对齐能力。

## SDD_16：常见误解 vs 真正要补的
- 常见误解：
  - 先写一堆文档
  - 写完放着不更新
  - 项目一忙就回到裸聊
  - 最后只剩形式感
- 真正要补的：
  - 给实现建立事实来源
  - 让 review 有共同参照
  - 让验证能对齐需求
  - 让变更可以追溯和交接
- 价值不在“写了什么”，而在“后面是否真的按它推进”。

## SDD_17：下一集预告
- 下一集主题：SDD 不是多写文档，它到底在补什么
- 要点：先把问题看清，再谈方法和工具

## SDD_18：一份 spec 最少回答什么
- 目标：这次做什么，为什么做；业务问题与范围
- 边界：能做什么，不能做什么；文件、接口、依赖限制
- 验收：最后如何判断完成；输出、测试、回归结果

## SDD_19：什么时候不必重工程化
- 可以先别上太重：
  - 探索型原型
  - 一两行的小改动
  - 紧急修复先止血
  - 强主观的临时试验
- 值得走 SDD：
  - 复杂功能迭代
  - 多人或多 agent 协作
  - 需要 review 和追溯
  - 做偏了返工很贵的任务
- 结论：不是所有地方都要工程化，但复杂任务不能一直靠感觉推进。

## SDD_20：更完整的 spec 内容
- 目标与价值：解决什么问题，为什么现在做；避免泛泛而谈
- 上下文与约束：依赖什么，受什么限制；已有架构和规范
- 输入输出：谁给什么，最后产出什么；接口、字段、文件
- 边界条件：异常、反例和禁止项；哪些场景不处理
- 验收标准：做到什么程度才算完；测试和结果门槛
- 技术要求：性能、安全、可维护性；避免实现失真

## SDD_21：一个功能级 spec 最小轮廓
- 目标：给订单列表增加导出能力
- 边界：只改列表与导出链路，不重构查询模块
- 输入输出：选择条件 → 导出文件
- 异常：无权限、导出超时、空数据
- 验收：接口可回归，结果可下载，日志可追踪

## SDD_22：下一集主题：OpenSpec 落地
- 主题：为什么 OpenSpec 更容易让 SDD 落地
- 核心观点：SDD 不是把开发变成文档劳动，而是给后面的实现和验证建立事实来源。

## SDD_23：OpenSpec 主路径概览
- Explore：先澄清需求与边界
- Propose：生成 proposal、design、tasks
- Apply：按清单实现并及时验证
- Archive：把增量并回主规范库

## SDD_24：review 顺序也会变化
- Step 1：先看目标和边界有没有写清
- Step 2：再看验收标准是否可执行
- Step 3：最后再看代码实现是否对齐 spec
- 价值：review 不再只是盯 diff，而是对齐共同事实来源。

## SDD_25：SDD EP03 开篇
- 主题：SDD 开发模式
- 副标题：OpenSpec 为什么更容易被真正用起来
- 核心问题：很多团队长期照着流程走很难。

## SDD_26：重流程体验 vs OpenSpec 体验
- 重流程体验：
  - 阶段很多
  - 命令记不住
  - 先学工具再做需求
  - 团队很容易半路放弃
- OpenSpec 体验：
  - 主路径很短
  - 四个动作容易形成习惯
  - 先解决需求，再补流程细节
  - 更适合日常迭代

## SDD_27：先把约束写稳再实现
- 被划掉：先写代码再补解释
- 主张：先把约束写稳再实现
- 核心观点：复杂项目真正浪费时间的通常不是设计，而是返工。

## SDD_28：OpenSpec 主路径短
- Explore：先澄清需求与边界
- Propose：生成 proposal、design、tasks、specs
- Apply：按清单实现并及时验证
- Archive：把增量并回主规范库
- 要点：流程越轻，越可能变成习惯。

## SDD_29：OpenSpec 降低的是门槛
- 命令少：主路径只有四个动作
- 工作全：proposal、design、tasks、specs 都有位置
- 可评审：先审意图，再审实现
- 可归档：变更能并回主规范库
- 结论：它降低的是采用门槛，不是把事情讲得更玄。

## SDD_30：结构化工作链 vs 只有聊天记录
- 只有聊天记录：
  - 讨论完就散
  - 后续靠记忆恢复
  - review 只能看 diff
- 有结构化工作链：
  - 意图、方案、任务分层沉淀
  - 后续可按文档恢复上下文
  - review 可以分阶段看问题
- 价值：结构化工作越主路径，协作越不像碰运气。

## SDD_31：探索阶段 vs 生产迭代
- 探索阶段：
  - 先跑出方向
  - 问题还在收敛
  - 可以先轻量一点
  - 后面再决定是否补规范
- 生产迭代：
  - 要考虑 review 与回溯
  - 改动要能交接
  - 存量系统不能随便漂
  - 更适合走完整规范闭环
- 结论：OpenSpec 更像生产级迭代主路径，不是替代所有探索行为。

## SDD_32：一条最小 OpenSpec 工作流
- 安装：`npm install -g @fission-ai/openspec@latest`
- 初始化：`openspec init`
- Explore：`/opsx:explore 给订单列表加导出功能`
- Propose：`/opsx:propose 增加订单导出能力`
- Apply：`/opsx:apply`
- Archive：`/opsx:archive add-order-export --yes`
- 核心路径：先初始化，再 explore，再 propose，再 apply，最后 archive。

## SDD_33：多智能体协作预告
- 主题：多智能体协作：先文档，再拆解
- 核心观点：OpenSpec 好用，是因为它把复杂流程压成团队愿意长期执行的最小动作。

## SDD_34：SDD EP04 开篇
- 主题：SDD 开发模式
- 副标题：多智能体真正难的不是执行，而是交接
- 核心问题：多智能体一开始容易想得很美。

## SDD_35：多智能体协作的三步
- 先 init：在项目里把规范层入口补起来；不用先追求复杂模板
- 先 propose：先生成可评审工作再实现；别一上来就 apply
- 做完 archive：把一次变更并回系统规范；避免文档慢慢失真

## SDD_36：并行方式对比
- 直接并行开干：
  - 每个 agent 自己理解需求
  - 接口和字段容易漂移
  - 合并时才暴露冲突
  - 返工成本很高
- 先文档再并行：
  - 目标和边界先写清楚
  - 任务按交付单元拆开
  - 接口和验收先对齐
  - 并行时更容易稳定收口
- 结论：协作不是把任务扔出去，而是先把共同事实立住。

## SDD_37：一次典型并行翻车链路
- Agent A：修改 response 字段结构
- Agent B：继续按旧字段补测试
- Agent C：合并分支并跑集成
- 问题：接口契约不一致，测试全部失效
- 结论：问题不是代码量，而是共享契约从未写清。

## SDD_38：多智能体协作的共同事实
- Goal：这次到底要交付什么
- Design：关键方案与边界怎么定
- Contracts：接口、字段、输入输出
- Acceptance：做到什么算完成
- 要点：多智能体要跑顺，先把共享事实从聊天变成文档。

## SDD_39：OpenSpec 默认留下什么
- proposal：解释为什么做这次改动；影响范围与风险
- design：记录实现路径和关键决策；技术方案与取舍
- tasks：拆成可执行清单；按任务推进并勾选
- specs：并回系统的长期规范；避免文档腐烂
- 价值：这组工作不是摆设，会直接影响 review、回顾、接手和后续迭代。

## SDD_40：讨论变成资产
- 被划掉：聊完就忘
- 主张：讨论变成资产
- 核心观点：工作的价值在于后续还会被持续使用。
- proposal 讲为什么做，design 讲怎么做，tasks 讲一步步怎么推进，specs 沉淀成长期规范。

## SDD_41：按人分活 vs 按交付单元拆
- 按人分活：
  - 谁想做什么就先做
  - 边界常常后置
  - 合并时才发现不匹配
- 按交付单元拆：
  - 先定输入输出
  - 接口契约先锁定
  - 每块都有完成标准
- 结论：多智能体并行之前，最关键的是拆解方式。

## SDD_42：按交付单元拆
- 被划掉：按人分工
- 主张：按交付单元拆
- 核心观点：任务能否并行，取决于边界是否独立、验收是否清楚。

## SDD_43：交付单元的三个文件
- proposal.md：说明目标、边界和风险；先让任务收口
- tasks.md：把任务拆成可勾选单元；便于派发与追踪
- handoff.md：记录当前状态和下一步；换人换 agent 都能继续

## SDD_44：60 秒起手动作
- `read proposal.md`
- `read contracts.md && read tasks.md`
- `assign Agent A -> API, Agent B -> UI, Agent C -> tests`
- 每个 agent 先明确输入、输出、互域、验收门。

## SDD_45：最小 handoff 说明
- Done：导出接口已补齐，字段契约已锁定
- Next：继续补下载测试和权限回归
- Risk：前端仍在使用旧字段，需要同步更新
- 要点：handoff 不求漂亮，先求下一棒能立即接上。

## SDD_46：并行条件
- 先别并行：
  - 接口还在变
  - 字段命名没锁定
  - 验收门不明确
  - 写域互相覆盖
- 可以并行：
  - 输入输出已固定
  - 契约已经成文
  - 任务边界互不干扰
  - 完成标准都能独立检查
- 结论：并行不是默认动作，很多任务其实应该先串行收口。

## SDD_49：SDD EP05 开篇
- 主题：SDD 开发模式
- 副标题：用四个动作跑通一次真实交付链
- 核心目标：把前面内容重新收回到一条最小闭环。

## SDD_50：最小闭环实操
- 主题：最小 SDD + OpenSpec 闭环实操
- 核心观点：今天就可以做一个很小的动作。

## SDD_51：更稳的三步拆法
- 定输入输出：先看这块接什么、产什么；接口、文件、状态
- 写契约：把字段和边界写清楚；别等到合并才对齐
- 设验收门：每块都知道怎样算完；测试、lint、回归

## SDD_52：起手：init / explore / propose
- 安装并初始化 OpenSpec
- 从一个很小但真实的需求开始：订单列表增加导出功能
- 执行 explore 与 propose
- 生成 `changes/add-order-export/...` 全套工作
- 要点：propose 的作用是先把本次变更收成可评审工作，而不是立刻开写。

## SDD_53：propose 阶段产物
- proposal.md：讲为什么做、影响哪些范围；先看意图对不对
- design.md：讲怎么实现、用什么方案；关键取舍先前置
- tasks.md：讲按什么顺序推进；任务拆到可执行
- specs/：讲这次新增或修改了什么规范；为 archive 做准备
- 价值：后续实现、review 和交接都会围着这些工作转。

## SDD_54：最小闭环四动作
- Explore：先把需求和边界聊清楚
- Propose：生成 proposal、design、tasks、specs
- Apply：按任务执行，不靠感觉一路冲
- Archive：把增量并回主规范库
- 关键：闭环不是动作本身，而是每一步都可看、可对齐、可继续推进。

## SDD_55：apply 阶段任务推进
- 示例任务：
  - 新增导出接口
  - 补服务层导出逻辑
  - 回归权限校验与下载测试
- 要点：每一步做完都回看 spec 与验收门。
- 核心观点：apply 不是一路往前冲，而是带着任务清单和验收止损推进。

## SDD_56：边做边验
- 被划掉：写完再一起验
- 主张：边做边验
- 核心观点：验证越后置，返工越贵。

## SDD_57：贯穿闭环的验证门
- 最后才统一检查的问题：
  - 问题晚暴露
  - 返工一改就是一串
  - 很难知道哪一步开始偏
- 每一步都带验证门：
  - 问题尽早暴露
  - 每块都知道怎么验
  - 偏了可以在当步修正
- 结论：验证不是尾声，而是贯穿整条闭环的动作。

## SDD_58：最少要盯住哪些验证门
- 边界门：有没有超出本次范围；避免顺手改太多
- 契约门：接口和字段是否一致；前后端都按同一份 spec
- 测试门：关键回归是否补齐；别把验证留到最后
- 检查项：是否偏离边界、接口是否对齐、测试是否补上、回归是否通过。

## SDD_59：收束与下一步
- 路线回顾：
  - 先看清复杂开发为什么会漂
  - 再用 spec 把事实来源立住
  - 用 OpenSpec 跑短而稳的主路径
  - 把协作和归档一起接上
- 下一步：不是学更多命令，而是挑一个真实需求自己跑一轮。
- 核心观点：AI 开发进入工程状态，不是多换几个模型，而是把需求、规范、实现、验证和交接接成一条链。

## SDD_60：先成文，再实现，再归档

- 主张：先成文，再实现，再归档

## SDD_62：Archive 的作用
- 不做 Archive：
  - changes 只停在临时目录
  - 代码改了，主规范没更新
  - 后续继续迭代时又要猜
- 做 Archive：
  - 增量规范并回主 specs
  - 系统现状可回看
  - 后续迭代有统一入口
- 结论：archive 不是收尾动作而已，它决定文档会不会腐烂。
