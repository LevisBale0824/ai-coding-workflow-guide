SDD 开发模式

EP01 · 问题

一次典型任务漂移

原始需求
  • 给订单列表加导出按钮
  • 功能简单，范围明确
实际漂移
  • AI 先重构列表页结构
  • 顺便统一目录规范
  • 新建临时结果目录
  • 测试未跑，验收未定义
原任务从"加导出"漂成"顺手改一片" —— 问题不是 AI 不会做，而是没有收口。
EP01 · 对比

聊天记录 vs 书面约束

只靠聊天记录
  • 目标讲过但没留底
  • 边界靠上下文记忆
  • 做到哪里凭感觉
先有书面约束
  • 目标有明确描述
  • 边界写进任务入口
  • 验收标准先定义好
EP01 · 分析

小任务顺手 vs 复杂任务失控

小任务顺手
  • 目标短、变量少
  • 上下文还在窗口里
  • 做完就结束，不需要接力
  • 出错范围通常比较小
复杂任务失控
  • 目标会持续变化
  • 边界和状态容易丢
  • 要跨文件、跨阶段接力
  • 没有统一验收就会越做越偏
EP01 · 根因

复杂开发失控的四个原因

01 目标漂移

需求边做边变，没人收口

02 边界不清

可改范围只在聊天里提过

03 状态丢失

上一轮决定没有沉淀下来

04 验收模糊

没有一致的完成标准

这些不是单次回答的问题，而是过程设计的问题。

EP01 · 方向

SDD 先补的三件事

目标

这次到底解决什么问题
功能边界先写清

边界

哪些能动，哪些别碰
目录、接口、依赖约束

验收

做到什么程度才算完
测试、输出、回归结果

复杂任务的关键，不是更会说，而是更会收口。
EP01 · 适用

适合 SDD 的任务类型

存量项目

老代码边界多，最怕顺手乱改；需要"改一处牵一片"的控制

多人协作

人和 AI 都需要统一入口；不能靠聊天接力

长链路任务

需求、设计、实现要能收口；阶段产物必须可追踪

要 review 的任务

先看意图，再看实现；不只盯裸 diff

EPISODE 02

SDD 不是多写文档

它到底在补什么？补的是一份共同事实来源

EP02 · 理念

先定义再实现

被划掉
  • 边聊边写
主张
  • 先定义再实现
不是拖慢开发，而是把返工前置消化。
EP02 · 定位

SDD 在更上层收口

TDD

先写测试，定义代码行为

BDD

先写行为，强调用户视角

技术规格

架构约束与实现前提

需求规格

功能目标与边界条件

SDD 把不同阶段的约束收进一份可执行事实来源。
EP02 · 价值

没有 spec vs 有稳定 spec

没有 SPEC
  • 目标靠聊天补充
  • 边界一忙就忘
  • 做完靠直觉判断
有稳定 SPEC
  • 目标可回看
  • 边界可对照
  • 验收可执行
spec 提供持续对齐能力。
EP02 · 澄清

常见误解 vs 真正要补的

常见误解
  • 先写一堆文档
  • 写完放着不更新
  • 项目一忙就回到裸聊
  • 最后只剩形式感
真正要补的
  • 给实现建立事实来源
  • 让 review 有共同参照
  • 让验证能对齐需求
  • 让变更可以追溯和交接
价值不在"写了什么"，而在"后面是否真的按它推进"。
EP02 · 最小集

一份 spec 最少回答什么

目标

做什么、为什么做
业务问题与范围

边界

能做、不能做什么
文件、接口、依赖限制

验收

如何判断完成
输出、测试、回归结果

不是增加流程，而是减少返工。
EP02 · 完整版

更完整的 spec 内容

目标与价值

解决什么问题，为什么现在做

上下文与约束

依赖什么，受什么限制

输入输出

谁给什么，最后产出什么

边界条件

异常、反例和禁止项

验收标准

做到什么程度才算完

技术要求

性能、安全、可维护性

EP02 · 示例

一个功能级 spec 最小轮廓

# 目标 给订单列表增加导出能力
# 边界 只改列表与导出链路，不重构查询模块
# 输入输出 选择条件 → 导出文件
# 异常 无权限 / 导出超时 / 空数据
# 验收 接口可回归，结果可下载，日志可追踪
EP02 · 判断

什么时候不必重工程化

可以先别上太重
  • 探索型原型
  • 一两行的小改动
  • 紧急修复先止血
  • 强主观的临时试验
值得走 SDD
  • 复杂功能迭代
  • 多人或多 agent 协作
  • 需要 review 和追溯
  • 做偏了返工很贵的任务
不是所有地方都要工程化，但复杂任务不能一直靠感觉推进。

EP03 · Review

review 顺序也会变化

Step 1
看目标和边界

有没有写清

Step 2
看验收标准

是否可执行

Step 3
看代码实现

是否对齐 spec

review 不再只是盯 diff，而是对齐共同事实来源。
EP03 · 对比

重流程体验 vs OpenSpec 体验

重流程体验
  • 阶段很多
  • 命令记不住
  • 先学工具再做需求
  • 团队很容易半路放弃
OpenSpec 体验
  • 主路径很短
  • 四个动作容易形成习惯
  • 先解决需求，再补流程细节
  • 更适合日常迭代
EP03 · 结构

结构化工作链 vs 只有聊天记录

只有聊天记录
  • 讨论完就散
  • 后续靠记忆恢复
  • review 只能看 diff
有结构化工作链
  • 意图、方案、任务分层沉淀
  • 后续可按文档恢复上下文
  • review 可以分阶段看问题
结构化工作越主路径，协作越不像是碰运气。
EP03 · 实操

一条最小 OpenSpec 工作流

npm install -g @fission-ai/openspec@latest
openspec init
# Explore：澄清需求
/opsx:explore 给订单列表加导出功能
# Propose：生成方案
/opsx:propose 增加订单导出能力
# Apply：按清单实现
/opsx:apply
# Archive：并回规范库
/opsx:archive add-order-export --yes
EP03 · 阶段

探索阶段 vs 生产迭代

探索阶段
  • 先跑出方向
  • 问题还在收敛
  • 可以先轻量一点
  • 后面再决定是否补规范
生产迭代
  • 要考虑 review 与回溯
  • 改动要能交接
  • 存量系统不能随便漂
  • 更适合走完整规范闭环
OpenSpec 更像生产级迭代主路径，不是替代所有探索行为。
EPISODE 04

多智能体协作

真正难的不是执行，而是交接

EP04 · 对比

并行方式对比

直接并行开干
  • 每个 agent 自己理解需求
  • 接口和字段容易漂移
  • 合并时才暴露冲突
  • 返工成本很高
先文档再并行
  • 目标和边界先写清楚
  • 任务按交付单元拆开
  • 接口和验收先对齐
  • 并行时更容易稳定收口
协作不是把任务扔出去，而是先把共同事实立住。
EP04 · 翻车

一次典型并行翻车链路

Agent A
修改 response 字段

改变了返回结构

Agent B
按旧字段补测试

使用了旧契约

Agent C
合并并跑集成

全部失效

问题不是代码量，而是共享契约从未写清。
EP04 · 共识

多智能体协作的共同事实

Goal

这次到底要交付什么

Design

关键方案与边界怎么定

Contracts

接口、字段、输入输出

Acceptance

做到什么算完成

多智能体要跑顺，先把共享事实从聊天变成文档。
EP04 · 产物

OpenSpec 默认留下什么

proposal.md

解释为什么做这次改动；影响范围与风险

design.md

记录实现路径和关键决策；技术方案与取舍

tasks.md

拆成可执行清单；按任务推进并勾选

specs/

并回系统的长期规范；避免文档腐烂

这组工作不是摆设，会直接影响 review、回顾、接手和后续迭代。
EP04 · 沉淀

讨论变成资产

被划掉
  • 聊完就忘
主张
  • 讨论变成资产
  • proposal 讲为什么做
  • design 讲怎么做
  • tasks 讲一步步怎么推进
  • specs 沉淀成长期规范
工作的价值在于后续还会被持续使用。
EP04 · 拆解

按人分活 vs 按交付单元拆

按人分活
  • 谁想做什么就先做
  • 边界常常后置
  • 合并时才发现不匹配
按交付单元拆
  • 先定输入输出
  • 接口契约先锁定
  • 每块都有完成标准
任务能否并行，取决于边界是否独立、验收是否清楚。
EP04 · 文件

交付单元的三个文件

proposal.md

说明目标、边界和风险
先让任务收口

tasks.md

把任务拆成可勾选单元
便于派发与追踪

handoff.md

记录当前状态和下一步
换人换 agent 都能继续

EP04 · 起手

60 秒起手动作

read proposal.md
read contracts.md && read tasks.md
assign Agent A → API, Agent B → UI, Agent C → tests
# 每个 agent 先明确：输入、输出、互域、验收门
EP04 · 交接

最小 handoff 说明

Done

导出接口已补齐，字段契约已锁定

Next

继续补下载测试和权限回归

Risk

前端仍在使用旧字段，需要同步更新

handoff 不求漂亮，先求下一棒能立即接上。
EP04 · 条件

并行条件

先别并行
  • 接口还在变
  • 字段命名没锁定
  • 验收门不明确
  • 写域互相覆盖
可以并行
  • 输入输出已固定
  • 契约已经成文
  • 任务边界互不干扰
  • 完成标准都能独立检查
并行不是默认动作，很多任务其实应该先串行收口。

EP05 · 起手

起手：init / explore / propose

  • 安装并初始化 OpenSpec
  • 从很小但真实的需求开始：订单列表增加导出功能
  • 执行 explore 与 propose
  • 生成 changes/add-order-export/... 全套工作
propose 的作用是先把本次变更收成可评审工作，而不是立刻开写。
EP05 · 产物

propose 阶段产物

proposal.md

为什么做、影响哪些范围
先看意图对不对

design.md

怎么实现、用什么方案
关键取舍先前置

tasks.md

按什么顺序推进
任务拆到可执行

specs/

新增或修改了什么规范
为 archive 做准备

后续实现、review 和交接都会围着这些工作转。
EP05 · 闭环

最小闭环四动作

01
Explore

先把需求和边界聊清楚

02
Propose

生成 proposal、design、tasks、specs

03
Apply

按任务执行，不靠感觉一路冲

04
Archive

把增量并回主规范库

闭环不是动作本身，而是每一步都可看、可对齐、可继续推进。
EP05 · 执行

apply 阶段任务推进

Task 1
新增导出接口
Task 2
补服务层导出逻辑
Task 3
回归权限与下载测试
apply 不是一路往前冲，而是带着任务清单和验收止损推进。
EP05 · 验证

贯穿闭环的验证门

最后才统一检查
  • 问题晚暴露
  • 返工一改就是一串
  • 很难知道哪一步开始偏
每一步都带验证门
  • 问题尽早暴露
  • 每块都知道怎么验
  • 偏了可以在当步修正
验证不是尾声，而是贯穿整条闭环的动作。
EP05 · 检查

最少要盯住哪些验证门

边界门

有没有超出本次范围
避免顺手改太多

契约门

接口和字段是否一致
前后端都按同一份 spec

测试门

关键回归是否补齐
别把验证留到最后

检查项

是否偏离边界、接口是否对齐
测试是否补上、回归是否通过

EP05 · 归档

Archive 的作用

不做 Archive
  • changes 只停在临时目录
  • 代码改了，主规范没更新
  • 后续继续迭代时又要猜
做 Archive
  • 增量规范并回主 specs
  • 系统现状可回看
  • 后续迭代有统一入口
archive 不是收尾动作而已，它决定文档会不会腐烂。
EP05 · 收束

先成文，再实现，再归档

被划掉
  • 光需求，等代码
主张
  • 先成文，再实现，再归档
  • 先看清复杂开发为什么会漂
  • 再用 spec 把事实来源立住
  • 用 OpenSpec 跑短而稳的主路径
  • 把协作和归档一起接上
真正的提升，不只是写得快，而是后面更稳、更能接力。
